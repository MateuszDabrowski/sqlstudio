# Changelog

All notable changes to SQL Studio are documented in this file.

## 1.4.2 - 2026-10-22

1.4.2 adds a lint rule for a run failure that an org test found in LEFT and SUBSTRING, names more causes in the hint of a failed run, and corrects the type of a Data Extension's Locale field. A second round of 169 org tests on 2026-10-20 and 2026-10-21 then shaped six lint changes, two refusals and a note in Save As, and five hints. A third round of 12 tests on 2026-10-21 added a lint rule for a key the query can return twice, widened the DATEDIFF rule, added three notes to Save As and a check of a taken name to Save to DE, and refined a hint, and a fourth round of 7 gave the Claude skill its last facts. Two more lint rules follow from those tests, MCE105 for an email address converted to a number and MCE106 for constant JSON that the query check refuses, and the texts about a line comment now say what the save does and no more. MCE107 and MCE108 report a text field converted to a date or a number and JSON read from a field with no ISJSON guard, which fail the run on one bad value, MCE097 is a warning for COUNT of a column, MCE102 reads a product that passes an int, and Save As notes a text as a date, a NULL into a required field and an EmailAddress field longer than its target. The org test of the first release candidate, round 5, then corrected MCE020 for Disk and Index, MCE106 to the parser that stops at the value, MCE103 for RIGHT, MCE102 for a whole number as a date, and Save As for a column the target lacks and a required field with a default. The org test of the second release candidate, round 6, then corrected the strict parser for `Disk` as a table alias, MCE106 for a bad value before the path's value, the Action Log's quote by type of conversion, the hint of Validate for constant JSON, the length note of Save As for Phone and EmailAddress fields, the stale look of Validate's answer and the check of a taken name in Save to DE. The org test of the third release candidate, round 7, then made `Disk` a plain name and corrected MCE106 to read the whole value at the path. Only the Frontend's code and the Claude skill change.

### Highlights

- **Built on 400 tests of MCE's SQL engine:** full check of queries the SQL Server engine refuses, breaks or fails on, and what it says when it does. Everything below comes from them.
- **Much better lint:** SQL Studio now flags the usual causes of a run that fails with no reason, no longer flags valid SQL that MCE accepts, and links each finding to the section of my articles that explains it.
- **New warnings in Save As:** Save As now warns before you save a Query Activity whose run would fail on a value too long for its field, text that is no date or number in a Date or Number field, a NULL in a required field or a repeated key.
- **Claude skill, updated:** SF MCE SQL now knows the new rules and the facts from those tests, so Claude writes SQL the way MCE runs it. Get it from Help > Write SQL with Claude.
- **Update only the Frontend:** if you run 1.4.0 or 1.4.1, replace only the Frontend Code Resource. The Backend and the Cloud Page are unchanged, so Help > About may still show Backend 1.4.0.

### What is in it

- **MCE103, a negative length in LEFT or SUBSTRING:** `LEFT(SubscriberKey, CHARINDEX('@', SubscriberKey) - 1)` on keys without an @ passed Validate and the save, and the run failed with status FatalError and no reason. A value without the character gives CHARINDEX 0, so the length is -1, and SQL Server refuses it with "Invalid length parameter passed to the LEFT or SUBSTRING function", which Marketing Cloud Engagement does not show. MCE103 is a warning on a LEFT length or a SUBSTRING length that is `CHARINDEX(...) - n` or `PATINDEX(...) - n`, as it fails only when a row lacks the character. RIGHT, which round 5 showed fails the same way, is read as LEFT is (see below). There is no finding where the query guards the call. That is a CASE WHEN or an IIF whose condition tests the same CHARINDEX (`> 0`, `>= 1`, `<> 0`) or a `LIKE '%c%'` of the same column, a WHERE with such a test joined by AND, or a search text with the character added to its end, as `CHARINDEX('@', x + '@')`. A WHERE guards the select list, but not a call in the same WHERE or in a join's ON, as SQL Server tests those conditions in no set order. A CASE guards no call inside an aggregate inside it, such as `MAX(LEFT(...))`, as SQL Server works out the aggregate before the CASE. Anything else is reported.
- **MCE103's fix:** Return NULL where the character is missing writes `NULLIF(CHARINDEX('@', x), 0) - 1`. LEFT and SUBSTRING then get a NULL length and return NULL for that row, where the whole run failed. The fix changes no result the query could produce, so it is in Fix all, and it keeps Format's layout. With `- 2` or more, a character before that position still gives a negative length, and the message says so.
- **The hint of a failed run names two more causes:** after a run that failed with no reason, the hint names a negative length when the query calls LEFT, RIGHT or SUBSTRING with a CHARINDEX or PATINDEX and a minus inside, with the NULLIF advice and MCE103. The list of causes SQL Studio has seen names a negative length and a value longer than its field too. A copy of 4,100 characters into a Text field of 4,000 ended in a failed run with no reason.
- **A Data Extension's Locale field is a varchar of 5 characters:** an org test read the SQL types of the fields of a Data Extension. Text, EmailAddress and Phone are nvarchar, Number is int, Decimal is decimal, Date is datetime and Boolean is bit. Locale is a varchar with a length of 5, where SQL Studio's data had it as an int. MCE098 reports `STRING_AGG(o.LocaleCode, ', ')` over a Locale field as it reports `_Subscribers.Status`, with the fix Cast to NVARCHAR(MAX), and MCE091 warns about VARCHAR(8000) for a separator that is no text value. MCE087 and MCE017 take a Data Extension's Locale field for text too, so a comparison with a number is a warning, and MCE087's message names the field's type, as MCE017's does. The Locale of a Data View, `_Subscribers.Locale`, was not tested, so it keeps the rules it had: `s.Locale = 1033` gets no warning.
- **MCE020 leaves AS Precision alone:** `AS Precision` passed the query check on Marketing Cloud Engagement, while `AS Key` and `AS Order` were refused with "Incorrect syntax near the keyword 'Key'." (round 2 org tests B21, B19 and B20). MCE020 called all three errors, with SQL Server's text. `PRECISION` is out of its list now. No other word of the list was tried, and `AS Precision` was tried only as a column alias.
- **MCE020 reports a reserved word as a table name:** `FROM Order` got MCE000's "FROM needs a table name after it ... near ORDER", where the query check said "Order is not a known data extension or system data view." (A42, where no Data Extension of that name existed). It is now one MCE020 error that says `Order` is a reserved word, with the fix Wrap in brackets, safe and in Fix all. The same goes for the word after `JOIN`, `APPLY`, a comma of a table list and `Ent.`, `FROM Ent.Order` to `FROM Ent.[Order]`. The fix brackets each use of the word as a qualifier too, `FROM Order WHERE Order.Total > 1` to `FROM [Order] WHERE [Order].Total > 1`. The message asks for the brackets if a Data Extension has the name, and else for a check of the spelling, as the brackets name only a Data Extension that exists. MCE000 and the MCE061 for the alias after the word (`o` of `FROM Order o`) give way to it, while a misspelt table joined after it keeps its MCE061, and `FROM Exec` and `FROM System_User` get no MCE005 or MCE063 beside it. The fix is left for review where a word follows that could continue the name, as `FROM Order Items` with no such table known. The clause words that can follow a `FROM` still to be written, `WHERE` and `ORDER BY` among them, stay MCE000's.
- **MCE102 reads DATEDIFF in seconds over 68 years:** `DATEDIFF(SECOND, '1900-01-01', DateJoined)` passed Validate and failed the run with no reason (C12), as the int result passes 2,147,483,647 seconds after about 68 years. A date constant against `GETDATE()`, `SYSDATETIME()`, `CURRENT_TIMESTAMP`, `GETUTCDATE()` and the like in `SECOND`, `SS` or `S` is an error when the span passes the int. Against a plain column it is a warning when the constant is more than 68 years from today, and says the date from which a value fails the whole run. Two date constants more than 68 years apart are an error. A constant within 68 years, as the Unix epoch until 2038, gets nothing. The fix is Use DATEDIFF_BIG, as for the milliseconds.
- **MCE015 is a warning where the query goes to an existing target:** `_Status` as an output column was saved with Append into an existing Data Extension, ran, and Marketing Cloud Engagement left the column out, as for any column the target lacks (D20). MCE015 blocked the save until Save anyway. Where the lint has a target, which it has in the editor for an opened Query Activity, in Save As and in Save to DE into an existing Data Extension, it is a warning that says so. It stays an error for Run, which writes into a temporary Data Extension, and where no target is known. The rename fix then needs review and is out of Fix all, as it fills a field of the new name, and MCE062 for a typo of such a name stays a warning.
- **MCE099 says the rows can fail to load at all:** a raw `HASHBYTES('SHA2_256', SubscriberKey)` ran, and SQL Studio could not fetch any row, "Could not fetch results: Internal Server Error", which was MCE's own REST error (C16). The message said a binary value can stop the rows from loading in SQL Studio and Contact Builder. It says now that it can stop them at all. A failed fetch with "Internal Server Error" gets a hint when the query outputs a binary value: it names MCE099 and its fix, writing the value as hex. A start or a save that MCE answers with the same words gets no such hint.
- **Save As refuses Update into a target with no primary key:** MCE refused the save with "Error saving the Query field.The Target Data Extension must have at least one primary key field." (D05). Save As says so under the update type, as it does for a target of key fields alone, and Save sends nothing but a toast, with no Save anyway.
- **Save As refuses a required target field the query leaves out:** MCE refused the save with "Error saving the Query field.Field 'EmailAddress' is a required for the Target Data Extension. Ensure this field is specified in your query text." (D12), where Save As only noted it and let the save go. A field that cannot be empty, is no primary key field and has no default value is now an error line in the check under the target, and Save sends nothing. A required field with a default value keeps the note, as that case was not tried, and so does every required field when SQL Studio cannot read the whole output, as a `SELECT *` over a table whose fields have not loaded. An edit of the text reads the output columns again, which the check kept from the dialog's opening.
- **Save As warns of text longer than its target field:** 19 characters written into a Text field of 10 with Append saved, and the run failed: the Action Log said "String or binary data would be truncated in table ..., column 'Note'. Truncated value: ..." (D15). The check now has a warning for an output column that is a plain reference to a Text field longer than the target's Text field, or a text literal longer than it, and says that one value that is too long fails the whole run. It reads only columns whose length is known: an expression, a call and a field of a derived table are left alone. It is a note and not a refusal, as the save succeeds. The same two checks, a required field and an update type, were already in Save to DE into an existing Data Extension. Plain Save of an opened Query Activity checks no target field, and MCE's refusal comes back as a toast with its own words and, for a required field, a hint.
- **Hints, the TRIM and IS DISTINCT FROM check:** `TRIM(BOTH '-' FROM OrderId)` got "OrderId is not a known data extension ...", and the hint told the user to check the spelling. The hint now names the FROM inside TRIM(... FROM ...) or IS DISTINCT FROM (MCE066) whatever name the check quotes, when the query holds one (A26).
- **Hints, the run that failed with no reason:** a `%` or `/` by a number other than 0, with a sign or in parentheses too, is no division by zero any more: `DATEFROMPARTS(2026, 2, 28 + SubscriberID % 2)` failed on a date that does not exist, and the hint had blamed the `%` (C11). The hint names that cause for DATEFROMPARTS, DATETIMEFROMPARTS, DATETIME2FROMPARTS, SMALLDATETIMEFROMPARTS and DATETIMEOFFSETFROMPARTS, with DATEADD from the first of the month as the way to roll over. Its overflow cause now names a multiplication, `SubscriberID * 1000000000` (C06), with CAST to BIGINT, and a DATEDIFF (C12), with DATEDIFF_BIG, besides DATEADD. A new cause names STRING_AGG with no MAX in its value, whose list failed past 4,000 characters, where the same list converted to NVARCHAR(MAX) ran at 5,444 (C14, C15b), with MCE091. The list of causes seen, shown when the query shows none, has all of these.
- **Hints, what the Action Log says:** the list said that Automation Studio's Action Log says only "Automation failed due to system error". Round 2 showed it names the reason for a text in a Number field ("Conversion failed when converting the nvarchar value '...' to data type int."), a NULL in a required field or a key ("Cannot insert a NULL value into a non-nullable column."), a value too long and a duplicate key ("Violation of PRIMARY KEY constraint ..."), and says only "Automation failed due to system error." for a division by zero, invalid JSON, an int overflow and a text date it cannot read (D02, D11, D13, D15, D17, D22, E07 to E10). The list says which, and that for all but the NULL the reason quotes the value, which can be a subscriber's data.
- **MCE104, a key of the target that the query can return more than once:** an Append whose result held one key twice failed the run even into an empty target and wrote nothing, with "Violation of PRIMARY KEY constraint ..." in the Action Log (G08). An Update failed the same way on a repeated key the target lacked (G09), and on keys it held it completed and kept the first row of each. An Overwrite kept one row for each key, the last in the source's read order, with no error, and the same rows on a second run (G10). MCE104 reads the target of the Query Activity like MCE050, and applies when the target has a primary key and the output gives every key field by name, without regard to case. It is a warning for Append and Update, and an info for Overwrite and for an action that is not known, and its message says what the action does, that Update keeps the first row of a repeated key the target holds and Overwrite the last it reads, and to keep one row for each key, for example with `ROW_NUMBER() OVER (PARTITION BY key ORDER BY ...) = 1` in a subquery. There is no finding where the query provably returns each key once: a `TOP 1`, a `SELECT DISTINCT` whose every column is a key column, a query of one row (no `FROM`, or an aggregate of all the rows with no `GROUP BY`), a `GROUP BY` whose every expression is among the key columns, a derived table or CTE that numbers its rows with `ROW_NUMBER() OVER (PARTITION BY p ...)` under a `WHERE` that keeps the number 1 with each `p` among the key columns, or one table whose own primary key fields are all key columns as plain references, with only inner, left, comma and cross joins to tables it matches on their whole primary key (the reading the Document diagram uses for a join's marks). A join that repeats that table's rows is let through under a `SELECT DISTINCT` of its own fields and of the tables it matches on their whole key, or a `GROUP BY` of them, as `SELECT DISTINCT s.SubscriberKey, s.EmailAddress` over `_Subscribers` joined to `_Sent`. Under `GROUPING SETS`, `ROLLUP` or `CUBE`, which add rows of NULLs beside each group's, only the first two hold. `_Subscribers.SubscriberKey`, `_Subscribers.SubscriberID` and `_Job.JobID` count as unique, [Likely] from the documentation of the Data Views and not from an org test. A `UNION ALL`, a join that can repeat a row and a table whose key is not known are reported. It has no fix, as the query has to pick the row. It never stops a Run, which has no key to compare with, or a save, which stops on errors only. The editor loads the fields of the opened Query Activity's target for it.
- **Save As notes the repeated key under the update type:** the note is MCE104 for the text, the chosen target and the chosen action, and it follows all three, a warning for Append and Update and an info for Overwrite. It never stops the save.
- **MCE102 reads DATEDIFF in milliseconds, microseconds and nanoseconds from any date:** the rule read these parts only with the Unix epoch. A date constant against `GETDATE()` and its kin is now an error when the span passes 2,147,483,647 of the part, about 24.8 days in milliseconds, 35.8 minutes in microseconds and 2.1 seconds in nanoseconds, and a warning within it that names the moment from which every run fails. Against a plain column it is a warning whatever the constant, as a date more than that from it, either way, fails the run and a date column's values span more. Two constants further apart than that are an error. The Unix epoch keeps its error against anything. The fix is Use DATEDIFF_BIG. A DATEDIFF in seconds that failed the run (G06) left only "Automation failed due to system error." in the Action Log.
- **Save As warns of text that is no number in a Number or Decimal field:** a text into a Decimal field failed the run with only "Automation failed due to system error." (G11), and into a Number field the Action Log named the value (D13). The check warns when an output column is a plain reference to a Text, EmailAddress or Phone field and goes into a Number or Decimal field, as one value that is no number fails the whole run, and when it is a text literal that the field does not take, which fails every row: no number for either, `'1.5'` for a Number field, which holds a whole number, and a blank text for a Decimal field, by SQL Server's rules for converting text. A text that may convert gets nothing. The Claude skill's `check --target` says the same.
- **Save As warns of a STRING_AGG list in a Text field with a length:** a list past 4,000 characters failed the run (G05), and one of 5,444 ran once its value was cast to NVARCHAR(MAX), which is MCE091's fix (C15b). [Likely] a Text field then fails on a list longer than its length, which was not run. The check warns for an output column that is a `STRING_AGG` call into a Text field with a length, and says a list longer than the field fails the run.
- **Save to DE asks Marketing Cloud Engagement before it refuses a taken name:** the Data Extensions were deleted in MCE, and Save to DE refused "A Data Extension named X is already there." until its list, the day's cache, was loaded again. A name the list holds is now checked with one `getDataExtensionDetails` call for its key, with the four extras left out, once for each Data Extension while the name stays taken. A Data Extension that is gone leaves the list, with the sidebar, completion and lint, and the name is free. One that is there keeps the refusal as it was. When the call fails, the refusal says SQL Studio could not ask, and a Reload the list button under it loads the list again.
- **Hints, the Action Log by the type of a conversion:** a CONVERT or CAST to DATE got two rows, "Could not convert date and/or time from string data type." and the system-error line, for text that is no date and for an impossible date in the right format (G04, H01, H03). A conversion to INT names the cause and quotes the value (D13). A conversion to DATETIME or DECIMAL (H02, H04), a text written into a Date field (D17) and into a Decimal field (G11) get only the system-error line. The hint of a failed run says so for a query that converts and in its list of causes seen, and says that the Action Log can take about 90 seconds and a refresh to show its entry (G11).
- **MCE105, an email address converted to a number:** `CAST(sub.EmailAddress AS INT)` passed Validate and the save, and the run failed with status FatalError and no reason. Automation Studio's Action Log of such a run quotes the address, "Conversion failed when converting the nvarchar value '...' to data type int.", and deleting the Query Activity does not delete the log. An email address holds an @, so it is never a number, and the conversion fails the run for every row with an address. MCE105 is an error on a `CAST` or `CONVERT` to INT, BIGINT, SMALLINT, TINYINT, DECIMAL, NUMERIC, FLOAT, REAL, MONEY, SMALLMONEY or BIT (and INTEGER, DEC and DOUBLE PRECISION) of a plain reference to a field the schema types as an email address: a Data Extension field of type EmailAddress, and `_Subscribers.EmailAddress`, `_Job.FromEmail`, `_Job.TestEmailAddr` and `_Job.BccEmail`. It also reads the field inside LOWER, UPPER, TRIM, LTRIM and RTRIM of one argument. `TRY_CAST`, `TRY_CONVERT`, `TRY_PARSE`, a Text field and a column of a derived table get nothing, and so does a call in a `CASE` or an `IIF` whose condition names the field, as in `CASE WHEN ISNUMERIC(EmailAddress) = 1 THEN CAST(EmailAddress AS INT) END`, which runs. The message says the run fails for every row with an address, and that the Action Log quotes the address and keeps it after the activity is deleted, for the types where the log is known or likely to: INT, BIGINT, SMALLINT, TINYINT and BIT. Round 6 found that BIGINT gives no value (see below). A conversion to DECIMAL gave only the system-error line in the log (H04), and FLOAT, REAL and MONEY are likely to give no value either, so for those types the message leaves the log out. Run and every save stop on it, as on any error.
- **MCE105's fix:** Use TRY_CAST (Use TRY_CONVERT for a CONVERT) renames the call, so the cast returns NULL where it failed the run. It changes no result the query could produce, as a row with an address failed the run, so it is in Fix all, and it keeps Format's layout. The column is NULL in every row afterwards, so the cast is worth a second look: it is often a slip for another field.
- **MCE106, constant JSON that the query check evaluates:** the check evaluates a `JSON_VALUE` of a constant and no other constant. `JSON_VALUE('not json', '$.orderId')` was refused at Validate with "JSON text is not properly formatted. Unexpected character 'n' is found at position 0." (B53), and `JSON_VALUE('{"orderId":"ORD-1042"}', 'strict $.couponCode')` with "Property cannot be found on the specified JSON path." (B54), where lint had shown MCE014 alone. MCE106 is an error on a `JSON_VALUE` of two text literals, the path one of simple steps (`$`, `.name`, `."quoted name"`, `[n]`), whose text fails a strict parse, or whose `strict` path the text, an object or an array, lacks. The message quotes MCE's answer. A column or an expression as either argument, a path of another syntax, a text that parses once its control characters and odd blanks (a byte order mark, a no-break space) are spaces, an empty text, a text of a top-level number, text or null, and a text that is JSON get nothing, and neither does JSON_MODIFY, which no test tried on a constant. A text or a path written `N'...'` is MCE068's, as the check refuses it with Incorrect syntax first. Round 5 changed how the text is read (see below): the check parses only as far as the path needs, and JSON_QUERY is read too.
- **MCE106's fix:** Use a lax path removes the word strict from the path, so `JSON_VALUE` returns NULL for the missing property. The query did not pass Validate before, so the fix changes no result the query could produce, and it is in Fix all. A text that is no JSON has no fix, as the JSON that was meant is yours to write.
- **Line comments, explained by their effect:** MCE100's messages, the hints after a failed save or run, the SQL data's note on comments, the Claude skill and the docs said that Marketing Cloud Engagement's save "loses everything after a line comment". That says more than is known: nobody knows how the save does it, and it does not join the lines. The texts now say what happens. For the syntax check a `--` comment ends with its line, as in any SQL editor. For the save a line comment is never closed, as the article on Marketing Cloud Engagement's SQL errors puts it, so everything below it becomes part of the comment, and the whole query where the comment comes first. A comment that closes the query fits none of that, as nothing follows it. It passes the save and the run fails with no reason, and the texts say so without explaining it. Only the wording changes: MCE100, its fix and its severity are the same.
- **MCE107, a text field converted to a date or a number:** one value that does not convert fails the whole run. Rounds 3 and 4 converted text to DATE (G04, H01 and H03: the Action Log said "Could not convert date and/or time from string data type." and then the system-error line), to DATETIME (H02) and DECIMAL (H04: only "Automation failed due to system error."), and rounds 2 and 5 an email address to INT (E07 and A04: the log quotes the value). MCE107 is an info on a `CAST` or `CONVERT`, not `TRY_CAST`, `TRY_CONVERT` or `TRY_PARSE`, of a plain reference to a Text or Phone field, also inside LOWER, UPPER, TRIM, LTRIM and RTRIM, to DATE, DATETIME, DATETIME2, SMALLDATETIME, DATETIMEOFFSET or one of MCE105's number types. The message says what the Action Log says for the type, where a test showed it, and nothing for a type no test tried, BIGINT, SMALLINT, TINYINT and BIT among them, which round 6 tried (see below). It is an info, as the data is often clean. An email field is MCE105's alone, and MCE087, MCE089 and MCE017 read other calls: a Text field compared with a number, a text literal beside a date field, and a plain column. There is no finding where the call sits in a CASE or an IIF whose condition names the same column, or where the WHERE of its SELECT has, among conditions joined by AND, `ISDATE(x) = 1` for a date type, `ISNUMERIC(x) = 1` for a number type, or TRY_CONVERT or TRY_CAST of the column to the same type `IS NOT NULL`, for a call outside that WHERE and the joins' ON. ISNUMERIC is 1 for a text that converts to any number type, so it passes '1.5' and '1e3', and round 5 saw '1.5' fail an int and '1e3' a Decimal field (B02). Where ISNUMERIC is the only guard of a conversion to an integer type or DECIMAL, the finding stays and says so.
- **MCE107's fix:** Use TRY_CAST (Use TRY_CONVERT for a CONVERT) renames the call, so the value that did not convert gives NULL. It is safe, as a run that passed gives the same rows, and it is not in Fix all, as it turns a failed run into NULL for the bad rows. The copies of one call in a SELECT, as in its GROUP BY and ORDER BY, are one finding and one fix, or SQL Server would refuse a GROUP BY that no longer matches the select list.
- **MCE108, JSON read from a field with no ISJSON guard:** `JSON_VALUE` of a column over a value that is not JSON failed the whole run with only "Automation failed due to system error." (C03, E09), and the same call behind `CASE WHEN ISJSON(x) = 1` ran (C04). MCE108 is an info on a JSON_VALUE or JSON_QUERY whose first argument is a plain column, with no ISJSON of that column in a CASE or an IIF around the call, before it, or in the WHERE of its SELECT as `ISJSON(x) = 1` (or `> 0`, `>= 1`, `<> 0`) among conditions joined by AND, for a call outside that WHERE and the joins' ON. A CASE guards no call inside an aggregate inside it. A text literal as the first argument is MCE106's, and a field the schema types as a Number, Decimal, Date or Boolean field gets nothing, as a JSON read of it is a type error of the query. The fix, Guard with ISJSON, wraps the call (and each copy of it in the SELECT) in `CASE WHEN ISJSON(x) = 1 THEN ... END`: safe, and not in Fix all.
- **MCE097 is a warning for COUNT of a column:** `SUM(OrderTotal) / COUNT(CouponCode)` grouped by subscriber failed for a subscriber with no coupon (C05, E08 and H05), as COUNT of a column counts no NULL. MCE097 was an info for any divisor that can be 0. It is a warning now where the divisor is COUNT or COUNT_BIG of a column, not COUNT(*), also inside a CAST or CONVERT or with an OVER, and its message says why. A SUM stays an info, with a message that says a SUM can be 0 for a group: no test failed on one, and a share of a total, `x / SUM(x) OVER ()`, is common. Any other divisor stays an info, and the NULLIF fix is the one it was.
- **Save As warns of a text that is no date month first, and of a text field in a Date field:** the session reads dates month first. '12/31/2026' and '2026-12-31' were written as 31 December 2026, and '31/12/2026' failed the whole run with only the system-error line (D17). The check warns of a text literal that reads as no date that way, which fails every row, and of a plain reference to a Text, Email, EmailAddress or Phone field into a Date field, where one value the session cannot read fails the run, and suggests `TRY_CONVERT(DATE, x, style)` in the query. A blank text, a month's name and a time alone are let through, as they are not known to fail. The Claude skill's `check --target` says the same.
- **Save As warns of a NULL into a required field or a primary key:** a NULL written into one failed every row, with "Cannot insert a NULL value into a non-nullable column." and then the system-error line in the Action Log (D11 and D22). The check warns for an output column that is NULL, or a CAST or CONVERT of NULL, with a name that is the primary key of the target or a required field with no default value. No test wrote a NULL into a required field with a default, so it gets no note. The skill's `check --target` warns for a required field, as its schema file holds no default value.

## 1.0.0 - 2026-09-29

The first public release. SQL Studio rebuilds Salesforce Labs' Query Studio as a Cloud Page App that runs entirely inside your Marketing Cloud Engagement account, with each user's own login and permissions.

### Highlights

- Four query tabs that run at the same time, each on its own Query Activity.
- Lint for what Marketing Cloud Engagement refuses, with one-click fixes, and a formatter that follows the author's SQL style guide.
- Results that keep their types: dates with their seconds, sorted as dates, numbers sorted as numbers, paged, and exported in full to CSV.
- No server outside your account: every call runs with your own login, and the code is open to audit.
- Sessions stored hashed and encrypted, and renewed in the background while you work.

### What is in it

- **Editor:** T-SQL highlighting, completion for the System Data Views, your Data Extensions and their fields, the known values of status and category fields, and hover documentation that links to the author's field references, Salesforce's documentation and Microsoft's T-SQL reference.
- **Checks before a run:** Validate uses Marketing Cloud Engagement's own query check, so what passes and which functions work match Automation Studio's Query Activities. SQL Studio's lint adds what that check misses, such as an unpaired apostrophe in a comment, a `FOR JSON` at the top level, a column name a Data Extension field cannot have, or a Text column compared with a Number one, with a fix for most.
- **Runs:** four tabs, each with its own query, results and Status, kept in your browser per Business Unit and user. A run writes into a temporary Data Extension with a one-day retention, in a SQL Studio folder, and a column that names a Date, Number, Decimal or Boolean field keeps that type. A run that fails while it runs says so, with the cause SQL Studio knows for it.
- **Results:** a paged, sortable grid. The first 2,000 rows read without an API call, and later rows in 2,000-row chunks. Export CSV reads every row, reusing what is already loaded.
- **Saving:** Save as, Open and Save for Query Activities, with a check of your columns against the target Data Extension, and history in the browser or, if your admin turns it on, in a Data Extension.
- **Deployment:** one Cloud Page and two Code Resources, "SQL Studio", "SQL Studio Frontend" and "SQL Studio Backend", and an Installed Package. The first sign-in creates the sign-in log, and the app then creates the error log and the SQL Studio folders itself. The settings are checked before the first sign-in, and a mistake is named, never shown.
- **Security:** the sign-in log keys each session by a hash of its id, and stores each access token encrypted and bound to its own row and user. Browser storage is per user. There are no refresh tokens: `docs/EXTENDING.md` explains why, and what adding them takes.
- **Updates:** once a day, SQL Studio checks the public repository for a newer release and shows an Update badge with its key changes.
