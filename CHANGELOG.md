# Changelog

All notable changes to SQL Studio are documented in this file.

## 1.1.1 - 2026-10-06

A Business Unit with thousands of Data Extensions loads its Data Extension list again, up to four times faster, page by page. Updating means replacing the code of SQL Studio Frontend and SQL Studio Backend: the settings stay as they are, and the Cloud Page changed only its version line, so it can stay too.

### Highlights

- A Business Unit with thousands of Data Extensions loads its Data Extension list again.
- The Data Extension list loads up to four times faster.
- The sidebar fills page by page while a large list loads.
- Replace SQL Studio Frontend and SQL Studio Backend: the Cloud Page stays as it is.

### What is in it

- **Large Business Units:** in 1.1.0 the list's first page asked for each Data Extension's description, send relationship and template. On a parent Business Unit with about 4,500 Data Extensions, Marketing Cloud Engagement stopped that page at its time limit (HTTP 408), and the sidebar said "Could not load Data Extensions". The list now asks for names, keys and folders alone, as 1.0 did. A list of up to 500 Data Extensions then reads all their details in one more call. In a larger one, a Data Extension reads its details with its fields, when it is used: in a query, opened in the sidebar or in a join. They are cached with the list for the day, and Reload keeps them. Until then its hover shows no description, send relationship or template, and JOIN completion offers it only once its fields have loaded.
- **Page by page:** a first load shows each page of up to 2,500 Data Extensions as it comes, with "Loading the list: 5,000 so far..." under them, so the sidebar, its search and completion work before the last page. MCE073 waits for the whole list.
- **The cache:** the browser keeps the list in half the space, so a Business Unit with 15,000 Data Extensions still fits. A list that is still too large is cached without its descriptions, which load again on use.
- **A faster Backend:** the Backend reads Marketing Cloud Engagement's answers in far fewer steps. On the author's account, the details of a list of 254 Data Extensions came in 3.0 seconds, where the same call took 13.0, and the list's plain page in under 5 seconds, where it took 9.8. Of those 9.8 seconds, 8.3 went to the Backend's own reading of the answer and 0.2 to waiting for it: a slow call's console line now gives that split.
- **API calls:** a list of up to 500 Data Extensions costs 1 call more per load, for its details. A larger one costs 1 call for each batch of up to 50 Data Extensions used for the first time that day.

## 1.1.0 - 2026-10-05

SQL Studio opens twice as fast, child Business Units see the parent's shared and synchronized Data Extensions, JOIN autocomplete writes whole joins, runs spend fewer API calls, and lint flags a mistyped table before Run. Updating means replacing the code of all three pieces: the settings stay as they are.

### Highlights

- SQL Studio opens twice as fast.
- Child Business Units see the parent's shared and synchronized Data Extensions, with ENT. added for you.
- JOIN autocomplete writes the whole join for Data Views and Data Extensions.
- Fewer API calls, a free export up to 1,999 rows, and its cost shown before the click.
- Mistyped Data Views and unknown Data Extensions flagged before Run, with fixes.

### What is in it

- **Child Business Units:** with SQL Studio installed in the parent, a child session lists the parent's shared and synchronized Data Extensions, each with a SHARED or SYNCED badge. The sidebar's tree shows them in its own folders of the same names (Shared Items, Synchronized Data Extensions), or in folders made up from the parent's folder names where the child has none, and leaves the muted ENT. prefix off their rows, which keeps more of each name in view. The tree has no Parent BU folder: a search lists them in a "Parent BU" group with their folder paths. Completion and inserts add ENT., hover and `SELECT *` read their fields, and lint still flags a parent's Data Extension written without ENT. A child install lists only its own Data Extensions. `docs/DEPLOYMENT.md` step 6 explains both.
- **Sidebar folders:** with the search box empty, the Data Extensions are a folder tree that follows Contact Builder's: MCE's own top folders in its order (Data Extensions, Salesforce Data Extensions, Synchronized Data Extensions, Shared Items), the Data Extensions root open and every other folder closed, empty folders shown, and the number of Data Extensions below each folder when it is above 0. The tree leaves out MCE's system tables, the names that start with an underscore, as Contact Builder does, and a search still finds them, except the ones the Data Views section lists. The folders cost 1 more API call when the list loads, and are cached with it. The list and its search do not wait for them, and a folder load that fails is not asked for again until Reload.
- **Sidebar rows:** the section titles sit at the sidebar's left edge, and each level steps in by the same amount. A click on a Data View or Data Extension row opens or closes its fields instead of inserting its name. Two icons at the row's right end, shown on hover or keyboard focus, insert its name (Insert name) or a SELECT of every field, and a long name has the whole row until they show. Insert name is a plus, and each field row has one too, shown the same way, which inserts the field's name as a click on the field does. The table icon reads "Insert table query (SELECT with all fields)", and a primary key field shows a key icon. Enter or Space on a field inserts its name and nothing else, where Enter used to add a line break after it. The Data Views and Data Extensions sections collapse on a click, and a collapsed section in a search shows its match count.
- **Recommended joins:** when you start typing the table after `LEFT JOIN`, or another join that takes an `ON`, completion lists first the System Data Views related to a table already in the query, then every table as before. Each Data View has one row, joined to the earlier table it shares the most key columns with, and no suggestion trips MCE046. Each row inserts the table, a free alias and the whole `ON` clause in the formatter's layout, such as `_Open AS o` with its JobID, ListID, BatchID, SubscriberID and `IsUnique = 1` conditions, and a taken alias gets a number. Data Extensions come as whole joins after JOIN too, as the Data Views do, such as `Contact_Salesforce AS cs` with `ON cs._ContactKey = sub.SubscriberKey` in one pick, from what the Data Extension list holds, so no field is loaded for the Data Extensions you do not pick. When you type the space after the `ON` of a join you typed yourself, or start typing there, completion offers the conditions to each related table first, and the space opens that list at once when a join is recommended. A whole join shows its table's icon, and a condition after `ON` the operator's. `_Subscribers` joins on SubscriberID. In a child Business Unit, the recommended joins, the table names completion offers and the sidebar's inserts all write `Ent._Subscribers` and `Ent._EnterpriseAttribute`, as the author's query does there. The 39 relationships come from the author's Data Views pages and the author's decisions. The details panel beside the list is open by default and shows the whole join under its label. Ctrl+Space hides or shows it, and SQL Studio keeps your choice in this browser.
- **Joins with Data Extensions:** a Data Extension in the query joins too, by column name without regard to case and only between columns of one type family, so no suggestion trips MCE017. It joins a Data View on the columns of one of the view's relationships, in the place of the view at its other end, such as a send log with the four send keys to `_Open` as `_Sent` does, or JobID to `_Sent` as `_Job` does, and otherwise on SubscriberKey. Its SubscriberID, SubscriberKey or SubID, the Send Log template's name, stands in for SubscriberID, so the template joins `_Open` on its four keys. A sendable field that maps to the Subscriber Key stands in for SubscriberKey, even beside a column of that name, and joins `_Subscribers` on it, while in the send key SubscriberID or SubID comes first. The `Id` of a synchronized `Contact_Salesforce` or `Lead_Salesforce`, the Salesforce record ID that Marketing Cloud Connect uses as the Subscriber Key, stands in for SubscriberKey when the Data Extension has no sendable field or subscriber column, so `_Subscribers` joins it on `cs.Id = sub.SubscriberKey`. Two synchronized Data Extensions never join each other on it or on a sendable field, as a contact's, a lead's and another connected org's record IDs never match. Each join's note says what it rests on: column names, with a reminder to check them, the send relationship, or Marketing Cloud Connect's Subscriber Key. A send-log view never joins on JobID alone when the Data Extension has a subscriber column, and the Data Extension never joins on ListID or BatchID alone. Two Data Extensions join on the key columns they share. A Data Extension picked from completion or inserted with the sidebar's Insert name starts its field load at once, so the conditions after its `ON` come with the first character. A Data Extension whose field list fails to load is not asked for again by the lint, completion or hover until Reload, so a lint pass no longer spends an API call on it.
- **Data Extension details:** hovering a Data Extension, in the editor or in the sidebar, shows its description, what it sends by (Sendable: ContactKey = Subscriber Key) and the template it was made from when its key is not a GUID, each when it has one. The text shows as it is written, and a web address in it is a link that shows where it goes. The details come in the Data Extension list call. If Marketing Cloud Engagement refuses one of them, the list asks again without it, which costs 1 or 2 more API calls once, and leaves it out until the next version, or for a day when the error names no property or a later page of the list was refused.
- **Run status:** SQL Studio reads each run's status by its task ID, so it tells a queued run from a running one, ends a failed run at once, and stops guessing with a 60-second wait. While Marketing Cloud Engagement has not yet picked a queued run up, as with four runs at once, SQL Studio waits up to 5 minutes for its status: through WSProxy with no API call in the Business Unit that holds SQL Studio, and with your own login for 1 API call a check in a child Business Unit, as a check cost there before. A run without a task ID works as before.
- **Typed results:** a run waits up to 5 seconds for the fields of the Data Extensions it reads, so the types of their columns hold even right after a page load, and a Boolean, a Decimal and a Date show the same text on every read path and in the CSV, as SQL returns it: `1` or `0`, the Decimal with its scale (`1.50`), and the date with `.mmm` when its milliseconds are not zero, so a shown value works in a `WHERE` condition as it is.
- **WSProxy in the Backend's own Business Unit:** SQL Studio uses WSProxy for run status, the check and clean-up of its own Query Activities and temporary Data Extensions, the parent's Data Extension names and fields, and Export CSV of up to 100 unsorted columns. WSProxy never signs in for another Business Unit and never creates, changes or starts anything for a user. Every failed WSProxy read falls back to your own login, with no error shown. Salesforce is said not to count WSProxy calls against the API limit, which its documentation does not say, so a run's summary shows them apart, as "5 API calls · 25 WSProxy", and hovering it splits each by step.
- **Export CSV:** in the Business Unit that holds SQL Studio, an export of up to 1,999 rows reads without an API call, sorted or not, and a larger unsorted one reads 2,500 rows at a time through WSProxy. Both write the same file as before. What an export costs shows next to Export CSV before you click, as "No API call", "1 API call", "29 API calls" or "2 WSProxy calls", and it follows the results, the sort, the page you are on and the chunks already loaded. Clicking the button asks nothing, its progress shows in the button and nothing covers the page, and an export without an API call says so when it is done. A dialog asks only when an export finds, while it runs, that it needs more than the label said. If the read without an API call fails, the export reads the rows as it reads a larger result, and if WSProxy fails, it reads all the rows again through the REST API: the message at the end then names the calls it spent. As the label said no call, that read spends 1 call at most before the dialog asks with the real cost, such as "Export 60,000 rows? It takes 29 more API calls." when the count was behind the rows.
- **Results header:** the filter above the grid says "Filter rows below" and is named "Filter the rows on this page of results" for screen readers and in its tooltip, so it is not taken for a filter of the whole result: it filters the page on screen only. The run summary names the temporary Data Extension as "Temp DE", with its name on hover and a link to it in Contact Builder when the stack is known: a long name no longer crowds the header. "Delete temp DE" is now "Delete results", and asks first, with Cancel focused, as the other actions that remove something do. In a narrow header, such as 1,280 px with the sidebar open, the row count and "Temp DE" give way, and "Delete results" stays whole.
- **Security:** every error message is masked for the client secret, the token key and access tokens before it reaches a response, the error log or a redirect. A run's task ID is bound to the user who started it, so a renewed session or a second window keeps reading its status through WSProxy and another user cannot, and an export's WSProxy read is bound to the user and the Data Extension it reads. Temporary Data Extension keys are compared without regard to case, as Marketing Cloud Engagement compares them.
- **History:** the History dialog says where your history is kept: in this browser only, or in Marketing Cloud Engagement for 90 days, where anyone with Data Extension access in that Business Unit can read it. Server-side history stays off unless your admin turns it on with `historyDE`, and `docs/DEPLOYMENT.md` now asks that question in step 4.
- **Lint:** MCE071 warns when a join between two send-log views leaves out some of JobID, ListID, BatchID and SubscriberID, which can repeat rows, and its fix adds them. It reads every `UNION` branch, subquery and CTE with its own tables, as MCE017 and MCE018 now do, and MCE046 now leaves those joins to it. Lint warns about a mistyped Data View such as `_Sents` (MCE072), and its fix renames the table's qualifiers too. It warns about a table that is no System Data View, not in the Business Unit's Data Extension list and not the query's own CTE or alias (MCE073), as MCE refuses it on Run only after some seconds. The warning names the time the list was loaded, has a "Reload the list" button in the Status tab and as a quick fix, and stays silent while the list loads or when part of it is missing. A toast says when its reload is done, and the sidebar keeps its tree on screen while the list reloads, with "Reloading the list..." in its footer. In a child Business Unit it checks `ENT.` names against the parent's list, and its fix adds `ENT.` to a parent's Data Extension written without it. A dangling `AND` or `OR` is an error, with a safe fix that removes it. Fix all takes a column fix that only drops a leading underscore or changes the letter case, says how many fixes it leaves for you, and then says how many it applied and whether new issues showed up. MCE033 leaves out a `GETDATE()` compared only with a System Data View date, which is server time too.
- **Contrast:** every token colour of the editor reads at 4.5:1 or more on its background in both themes, with keywords and Data View names a shade lighter in the dark theme, functions, strings and operators a shade darker in the light one, and `CASE`, `WHEN`, `THEN`, `END` and a block comment's `/*` and `*/` in the editor's own keyword and comment colours. The warning, error and info words in the Status tab, the banners and the query tabs read at 4.5:1 or more in both themes, and the light theme's warning squiggles and marks at 3:1.
- **Background renewal:** the background sign-in no longer loads the whole app in its hidden frame. The Cloud Page tells the app the sign-in has finished and stops there, so the frame skips the editor's loader and the Frontend, which a renewal that took 24 seconds on the author's org had loaded and parsed in the app's own thread. A Cloud Page from before this release still works, as the Frontend then does the same after it has loaded, which is slower.
- **Frontend files:** the Frontend comes in two files. `sql-studio-frontend.min.js` is the one to paste, at about half the size of `sql-studio-frontend.js` because it has no comments, blank lines or indentation, and `sql-studio-frontend.js` is the same code with its comments, for reading. Marketing Cloud Engagement served the `.min.js` in 2 seconds and the readable file in 18 on the author's account, so SQL Studio opens about 16 seconds sooner with the `.min.js`. The readable file's first line says to paste the other.
- **Opening times:** the console says once where the opening time went, for example "[SQL Studio] Opened in 18.2 s: the page arrived at 6.1 s, the Frontend started at 12.3 s, the editor was ready at 16.0 s, and whoami answered at 17.9 s." A time the browser cannot give is left out of the line. A run that ends on its status row says when MCE completed it, by the row's CompletedDate, and when SQL Studio read that, so a slow run shows whether MCE or the status checks took the time.
- **Fixes:** a free row count that answers fewer rows than the Data Extension holds no longer makes a run, a sorted or turned page, a restored result or an export show too few rows: SQL Studio reads that page again through the REST API, and a run that ends with no rows counted confirms it there for 1 API call. After `LEFT` or another join word, completion writes the whole join, such as `LEFT JOIN`, and after a finished join it offers keywords, not functions. After the table of a join, completion lists `ON` first, with no `OR`, `ORDER BY` or `OFFSET FETCH`, and an alias typed after a table stays as typed: one letter there opens no list. A Data Extension that Marketing Cloud Engagement lists under a System Data View's name, such as `_MobileAddress` or `_EnterpriseAttribute`, no longer stands in for the Data View in hover, lint and completion, and completion lists that Data View once. The retention notice no longer calls the sign-in log's encrypted tokens live, and the code's comments no longer point to documents the public repository does not have. A tab restored after its temporary Data Extension was deleted says its results are gone and forgets them, so later page loads no longer spend an API call asking for them. A restored tab whose results fail to load for any other reason, such as a network error or a timeout, keeps them for the next page load and shows the error, where it used to forget them. In a child Business Unit, a restored tab's next page and each new sort read the REST chunk that holds them, where they first read one page through the REST API for 1 API call more. A child run whose status is not there yet no longer ends on the first rows its page 1 shows, which can be a share of them while the query still writes: SQL Studio asks Marketing Cloud Engagement whether the query still runs, and reads page 1 again once it has finished. Cmd/Ctrl+A after Marketing Cloud Engagement's page had the keyboard focus, as it does after a reload and sometimes on its own, no longer selects that page and paints SQL Studio's frame blue: the frame takes the focus back when the pointer moves over it, and the editor takes it as soon as it is ready. A field list or a Data Extension list asked for when the session had lapsed now loads once the background renewal is done, where it used to need a second click or a page reload, and a request still in flight during a renewal no longer starts a second sign-in. While that renewal runs, an amber toast says so, and a green one says when it is done, or an amber one asks to try again what did not go through meanwhile, where the field list used to read "Loading fields..." for several seconds with no word why. A request that Marketing Cloud Engagement refuses with HTTP 429, as it did for a restored tab's results while four tabs asked at once, now waits and tries again up to three times, after about 1.5, 3 and 6 seconds, where that changes nothing (a run or a save is not sent again, and says to wait a few seconds and try again), and restored tabs read their results one after another, the tab on screen first.

## 1.0.0 - 2026-09-29

The first public release. SQL Studio rebuilds Salesforce Labs' Query Studio as a Cloud Page App that runs entirely inside your Marketing Cloud Engagement account, with each user's own login and permissions.

### Highlights

- Four query tabs that run at the same time, each on its own Query Activity.
- Lint for what Marketing Cloud Engagement refuses, with one-click fixes, and a formatter that follows the author's SQL style guide.
- Results that keep their types: dates with their seconds, sorted as dates, numbers sorted as numbers, paged, and exported in full to CSV.
- No server outside your account: every call runs with your own login, and the code is open to audit.
- Sessions stored hashed and encrypted, and renewed in the background while you work.

### What is in it

- **Editor:** T-SQL highlighting, completion for the System Data Views, your Data Extensions and their fields, the known values of status and category fields, and hover documentation that links to the author's field references, Salesforce's documentation and Microsoft's T-SQL reference.
- **Checks before a run:** Validate uses Marketing Cloud Engagement's own query check, so what passes and which functions work match Automation Studio's Query Activities. SQL Studio's lint adds what that check misses, such as an unpaired apostrophe in a comment, a `FOR JSON` at the top level, a column name a Data Extension field cannot have, or a Text column compared with a Number one, with a fix for most.
- **Runs:** four tabs, each with its own query, results and Status, kept in your browser per Business Unit and user. A run writes into a temporary Data Extension with a one-day retention, in a SQL Studio folder, and a column that names a Date, Number, Decimal or Boolean field keeps that type. A run that fails while it runs says so, with the cause SQL Studio knows for it.
- **Results:** a paged, sortable grid. The first 2,000 rows read without an API call, and later rows in 2,000-row chunks. Export CSV reads every row, reusing what is already loaded.
- **Saving:** Save as, Open and Save for Query Activities, with a check of your columns against the target Data Extension, and history in the browser or, if your admin turns it on, in a Data Extension.
- **Deployment:** one Cloud Page and two Code Resources, "SQL Studio", "SQL Studio Frontend" and "SQL Studio Backend", and an Installed Package. The first sign-in creates the sign-in log, and the app then creates the error log and the SQL Studio folders itself. The settings are checked before the first sign-in, and a mistake is named, never shown.
- **Security:** the sign-in log keys each session by a hash of its id, and stores each access token encrypted and bound to its own row and user. Browser storage is per user. There are no refresh tokens: `docs/EXTENDING.md` explains why, and what adding them takes.
- **Updates:** once a day, SQL Studio checks the public repository for a newer release and shows an Update badge with its key changes.
